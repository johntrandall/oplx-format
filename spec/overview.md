# Overview

An `.oplx` document is a container for an OmniPlan project. Two equivalent on-disk forms:

| Form | UTI | On-disk |
|---|---|---|
| Directory bundle (default for new docs in 4.10.x) | `com.omnigroup.omniplan2.planfile` | A directory |
| Zip variant | `com.omnigroup.omniplan2.planfile-zip` | A flat zip file |

OmniPlan accepts either; the file extension `.oplx` covers both.

## Bundle contents

A minimal valid `.oplx` (zip variant) contains exactly **3 files at the top level**:

```
out.oplx (zip)
├── __TOC.xml           # Project-level metadata, scenario index
├── __changelog.xml     # Operational mutation log
└── Actual.xml          # The "Actual" scenario (tasks, resources, deps)
```

A typical doc adds:

```
├── Preview.png         # QuickLook preview (auto-generated by OmniPlan on save)
└── <Baseline-N>.xml    # 0+ additional baseline scenario files
```

Directory-bundle equivalent:

```
out.oplx/
├── __TOC.xml
├── __changelog.xml
├── Actual.xml
├── QuickLook/
│   └── Preview.png     # NOTE: in QuickLook/ subdir for the directory bundle ONLY
└── <Baseline-N>.xml    # baseline scenario files at the top level (not in QuickLook/)
```

**Critical difference between forms**: in the **zip variant**, `Preview.png` is at the **top level** with no `QuickLook/` parent. In the **directory bundle**, `Preview.png` lives **inside** `QuickLook/`. Hand-zipping a directory bundle as-is (with `QuickLook/Preview.png` inside) produces a doc OmniPlan will silently refuse to open.

## XML namespace

Every XML file uses the namespace `http://www.omnigroup.com/namespace/OmniPlan/v2`. The default xmlns is `v2`; many files also declare `xmlns:opns` or `xmlns:opnx` as aliases (functionally equivalent).

## Scenarios

A document has one **Actual** scenario plus zero or more **Baseline** scenarios. Each scenario is a separate XML file; `__TOC.xml`'s `<project>` block lists them all:

```xml
<project>
  ...
  <scenario id="..." name="Actual" filename="Actual.xml"/>
  <scenario id="..." name="Baseline 2026-05-01" filename="Baseline-2026-05-01.xml"/>
</project>
```

The scenario file's root `<scenario id="...">` matches the id in `__TOC.xml`. Each scenario has its own task tree, resource tree, and schedule — they need not be structurally identical (a baseline is a frozen snapshot, while the Actual continues to evolve).

See [`changelog-xml.md`](changelog-xml.md) for how OmniPlan logs which scenario is being edited and the sequence of changes within a session.

## Prototypes (optional)

`Actual.xml` MAY contain `<prototype-task>` and `<prototype-resource>` elements at the top of the scenario. These are templates OmniPlan uses when the user creates a new task/resource via UI. They are **NOT required** — a doc with zero prototypes opens cleanly. OmniPlan strips empty/default-shaped prototypes on save anyway.

When emitted, the conventional set is 3 prototype-tasks (Task, Milestone, Group) + 1-2 prototype-resources (Staff, Equipment).

## ID conventions

| Entity | ID format | Examples |
|---|---|---|
| Task | `t<N>` (positive integer) | `t1`, `t77`, `t504` |
| Special tasks | `t-<N>` (negative) | `t-1` (root task), `t-2/t-3/t-4` (prototype tasks) |
| Resource | `r<N>` (positive integer) | `r1`, `r5` |
| Special resources | `r-<N>` (negative) | `r-1` (root resource), `r-2/r-3` (prototype resources) |
| Scenario | Opaque (base64-style or freeform) | `lPF-Nw4DT1i` (UI-created); `BLN-2026-05-01` (hand-edit OK) |

`__TOC.xml` tracks `<next-task-id>` and `<next-resource-id>` counters. **OmniPlan recomputes these on every save** to `max(used-id) + 1` — hand-bumped values do NOT survive (Cycle 0011 in the research repo).
